# MonSet-PLC — Полное понимание продукта (Product Specification)

> Версия 1.0 · 15.08.2026
> База: MonSet-main-2, ветка migration. Статус: концепт-документ, основа для планирования разработки.

---

## 1. Видение продукта

**MonSet-PLC** — промышленный мониторингово-управляющий комплекс класса «мини-ПЛК + IoT-шлюз» для удалённых и автономных объектов. Устройство работает в рантайме как ПЛК (скан-цикл, LAD-программирование через веб), собирает данные с датчиков и собственных I/O, ведёт попараметричные архивы на SD, передаёт телеметрию по приоритетной цепочке каналов связи и отдаёт данные в SCADA по Modbus TCP с ручной сборкой карты регистров.

**Формула продукта:** ПЛК (логика + I/O) + регистратор (архивы на SD) + шлюз (4 канала связи) + SCADA-интерфейс (Modbus TCP) — в одном устройстве, без перепрошивки, всё через веб.

## 2. Режимы работы (пересмотр текущей модели)

Текущая модель «веб-режим останавливает опрос» заменяется на PLC-модель:

| Режим | Поведение |
|---|---|
| **RUN** | Скан-цикл логики + опрос датчиков + архивация + передача. Веб-сервер работает параллельно, опрос НЕ останавливается |
| **RUN + WEB** | Браузер подключён — логика продолжает работать. Приоритет CPU: скан-цикл > опрос > веб |
| **PROG (STOP)** | Только на момент заливки новой LAD-программы: выходы → safe state, загрузка, верификация CRC, RUN |
| **SAFE** | Авария (обрыв датчика, сбой логики): выходы в безопасное состояние, авария в лог и на сервер |

## 4. Модель параметра (ядро системы)

Всё, что мониторится и управляется — **параметр**. Единый реестр в `runtime_config.json`:

```json
{
  "parameters": [
    {
      "id": "level_1",
      "name": "Уровень резервуара 1",
      "source": "modbus_rtu://usart3/dev5/reg10",
      "type": "float",
      "unit": "м",
      "metric": "water_level",
      "scale": 0.001,
      "poll_enabled": true,
      "backup_enabled": true,
      "backup_file": "/backup/level_1.jsonl",
      "backup_quota_kb": 2048,
      "send_enabled": true,
      "send_channels": ["eth", "gsm"],
      "mbtcp_enabled": true,
      "mbtcp_address": 100,
      "mbtcp_reg_type": "holding",
      "mbtcp_data_type": "float32",
      "mbtcp_word_order": "ABCD",
      "alarm_low": 0.5,
      "alarm_high": 4.5
    }
  ]
}
```

Источники параметра: Modbus RTU (USART3/UART4/UART5), Modbus TCP master (LAN через W5500), внутренние I/O (DI/AI), вычисляемые (LAD-меркеры %MW), системные (батарея, uptime, качество связи).

## 5. Подсистема бэкапа (переработка sd_backup.cpp)

### 5.1 Принципы

- **Попараметрично:** у каждого параметра свой файл бэкапа, своя метрика, своя галочка «создавать бэкап» в веб-интерфейсе (`backup_enabled`)
- **Ничего не терять до переполнения:** отправленные данные НЕ удаляются — остаются архивом
- **Кольцевая перезапись:** место кончается → удаляются самые старые данные

### 5.2 Формат хранения

JSONL, одна строка — одно измерение (совместимо с текущим backup.jsn):

```json
{"ts":"2026-08-15T23:00:01Z","v":4.273,"q":0}
```

`q` — качество: 0 = good, 1 = sensor fail, 2 = comm fail, 3 = обрыв 4–20 мА, 4 = расчётное.

### 5.3 Сегментная ротация (почему не один файл)

FAT не умеет дёшево обрезать начало файла. Поэтому каждый параметр — набор сегментов:

```
/backup/level_1.0001.jsonl
/backup/level_1.0002.jsonl   ← активный (пишется)
/backup/level_1.0003.jsonl
```

- Сегмент заполнен (256 KB, настраивается) → открывается следующий
- Переполнение квоты параметра (`backup_quota_kb`, по умолчанию 2 MB) или свободного места SD → удаляется самый старый сегмент (сначала полностью отправленные)
- Удаление сегмента — атомарная операция, безопасна при пропадании питания

### 5.4 Курсоры отправки

`/backup/cursors.json` — для каждого параметра: последний отправленный сегмент + смещение. Переживает перезагрузку и IWDG-сброс. Это заменяет текущую схему «отправил → стёр».

### 5.5 Алгоритм передачи (Backup Uploader)

```
Каждый цикл отправки (по своему расписанию, независимо от опроса):
1. Канал связи доступен? (channel_manager) — нет → выход
2. Скан /backup/: есть параметры с неотправленными данными? — нет → выход
3. Для каждого такого параметра (по очереди, в порядке приоритета/возраста):
   a. Прочитать с курсора порцию записей (пачка до N записей / лимит payload канала)
   b. Сформировать payload (ThingsBoard JSON / MQTT / Webhook)
   c. Отправить → успех: сдвинуть курсор, записать cursors.json
             → ошибка: стоп, повтор в следующем цикле (данные на месте)
4. Iridium SBD: отдельный компактный бинарный формат (≤340 байт MO),
   только критичные параметры (флаг send_channels включает "sbd")
```

## 6. Передача данных

- Приоритетная цепочка (как сейчас): **Ethernet → GSM → WiFi → Iridium SBD**, настраивается
- Протоколы: HTTPS, MQTT (ThingsBoard / HA / Yandex IoT / Node-RED), HTTP Webhook
- Дискретность отправки независима от дискретности опроса (как сейчас)
- **Тест отправки** (расширение текущей кнопки): выбор параметра и канала → одиночная отправка → результат (OK/ошибка/время) на странице и в лог
- Watchdog на каждый канал (как сейчас)

## 7. Modbus TCP (расширение modbus_tcp_slave.cpp)

### 7.1 Slave с ручной картой регистров

Веб-страница «Modbus TCP» — конструктор карты:

| Параметр | Адрес | Тип регистра | Тип данных | Порядок слов | Масштаб |
|---|---|---|---|---|---|
| level_1 | 100 | Holding (4x) | float32 | ABCD | — |
| pressure_1 | 102 | Holding (4x) | uint16 | — | ×0.01 |
| pump_1_state | 10 | Coil (0x) | bool | — | — |

- Адреса и порядок — **полностью вручную**, любые «дырки» в карте
- Поддержка Coil / Discrete Input / Input / Holding
- Типы: uint16, int16, uint32, int32, float32 + word order ABCD/BADC/CDAB/DCBA
- До 4 одновременных TCP-клиентов (SCADA + HMI + инженерный ноутбук)
- Доступность: Ethernet и WiFi — напрямую; **через GSM — только с публичным APN или VPN-туннелем** (NAT сотовых сетей не пропускает входящие); **через Iridium — невозможно** (SBD — сообщения, не TCP). Для GSM без APN: альтернатива — MQTT/HTTPS push (уже есть)
- Защищённый вариант: Modbus/TCP Security (MBAPS), порт 802, TLS + mTLS — см. SECURITY.md

### 7.2 Master (как сейчас)

Опрос Modbus TCP устройств в LAN — источник параметров наравне с RTU.

## 8. PLC Runtime (новое)

- Скан-цикл 50–100 мс: чтение входов → LAD-ранги → запись выходов → телеметрия
- LAD-редактор в вебе (`www/lad.html`), программа — JSON на SD (`/lad/program.json`), интерпретатор `lad_runtime.cpp` (контакты, катушки, TON/TOF/TP, CTU/CTD, сравнения, ПИД)
- Адресация IEC: %IX (DI), %QX (DO), %IW (AI), %QW (AO), %MW (меркеры), маппинг на параметры
- Retentive-память (счётчики, меркеры) — Flash sector 6–7 / файл на SD
- Лимиты v1 (приняты): 128 ранг / 1024 элемента / 2 ПИД-контура
- I/O: 5 DI / 5 DO на GPIO (PE3–PE12), 3 AI / 3 AO через ADS1115 + MCP4728 на I2C1, либо внешние Modbus I/O модули — оба пути живут в одной модели параметров

## 9. Логирование и аудит (расширение circular_log.cpp)

| Поток | Содержимое | Хранение |
|---|---|---|
| Runtime-лог | INFO/WARN/ERROR/DATA — как сейчас | RAM ring → веб-вкладка + `log_YYYY-MM-DD.txt` |
| Аудит действий | Вход в веб, смена конфига, заливка LAD, force DO/AO, смена пароля, тест отправки | `/logs/audit_YYYY-MM.log` — несбрасываемый |
| События логики | Срабатывание правил, аварии, переходы RUN/STOP/SAFE | `/logs/events_YYYY-MM.log` |
| Данные | Попараметричные архивы | `/backup/*.jsonl` (раздел 5) |

Веб-вкладка «Логи»: фильтр по потоку/уровню/параметру, автообновление, скачивание, очистка.

## 13. Нефункциональные требования

- **Надёжность:** IWDG ~32 c (как сейчас); переживание сброса — курсоры и конфиг на SD; атомарные операции с сегментами; safe state выходов при любом сбое
- **Ресурсы:** Flash 512 KB (контроль по .map — web_server.cpp 385 KB исходника требует рефакторинга), RAM 192 KB (пик — TLS-хендшейк; LAD ≤ 35 KB; буферы сегментов по 4 KB)
- **Безопасность:** см. docs/SECURITY.md (IEC 62443-4-2, MBAPS, APN, WireGuard)
- **Офлайн-первое:** весь веб без CDN; работа объекта без связи — полная автономность логики

## 14. Принятые решения (15.08.2026)

1. Размер сегмента бэкапа: 256 KB; квота на параметр: 2 MB — **принято**
2. Лимиты LAD: 128 ранг / 1024 элемента / 2 ПИД — **принято**
3. Пин ADC батареи — назначается свободный (не PA4/PB1/PC5, они зарезервированы под AI)
4. Все файлы (конфиг, бэкапы, логи, www) — на microSD платы, как сейчас
5. Modbus TCP через GSM — выделенный APN + MBAPS (порт 802) + опционально WireGuard
