# MonSet — Архитектура промышленной безопасности

> Версия 1.0 · 15.08.2026
> Дополнение к PRODUCT_SPEC.md. Отвечает на вопрос: как сделать устройство промышленно-безопасным, включая Modbus TCP через GSM.

---

## 1. Модель угроз (что защищаем)

| Угроза | Вектор | Последствие |
|---|---|---|
| Перехват/подмена телеметрии | GSM-канал, публичный интернет | Ложные данные в SCADA |
| Несанкционированное управление | Modbus TCP 502 порт, веб-интерфейс | Включение насосов/клапанов злоумышленником |
| Подмена прошивки/логики | Физический доступ, SD-карта | Полный захват устройства |
| Кража учётных данных | Чтение SD, снятие Flash | Доступ к облаку и сети заказчика |
| DoS | Флуд соединений на веб/Modbus | Потеря мониторинга объекта |
| Сканирование через сотовую сеть | Публичный IP устройства | Компрометация через открытые порты |

## 2. Три уровня защиты (defense-in-depth)

```
Уровень 1 — СЕТЬ:      выделенный APN оператора (изоляция от публичного интернета)
Уровень 2 — ТРАНСПОРТ: Modbus/TCP Security (TLS, порт 802, mTLS) или WireGuard-туннель
Уровень 3 — УСТРОЙСТВО: IEC 62443-4-2 — RBAC, secure boot, аудит, DoS-защита
```

### Уровень 1. Выделенный APN (сетевая изоляция)

Стандартная российская M2M-практика: закрытая точка доступа у оператора (МТС «Защищённая передача данных APN», Билайн «Выделенный APN»). Устройства заказчика — в изолированной частной сети без выхода в публичный интернет, с фиксированными приватными IP; стык с сетью заказчика — через L2TP/IPsec до площадки оператора. Modbus TCP ходит внутри частной сети, проблема NAT исчезает.

- Плюсы: ноль кода в устройстве, решает NAT, привычно для российских заказчиков
- Минусы: шифрование не end-to-end (доверие оператору), услуга платная, привязка к оператору
- Вывод: **обязательная опция для корпоративных поставок, но не единственная мера**

### Уровень 2. Защищённый транспорт — два режима на выбор

#### Режим A: Modbus/TCP Security (MBAPS) — основной

Официальная спецификация Modbus Organization (2018+):

- Классический Modbus PDU инкапсулируется в TLS **без изменений прикладного протокола**
- Порт **802** (классический 502 остаётся для LAN), TLS 1.2 минимум, рекомендуется 1.3
- **Обязательная взаимная аутентификация X.509v3** — и сервер (устройство), и клиент (SCADA) предъявляют сертификаты; роль клиента может кодироваться в расширениях сертификата
- Реализация в MonSet: обёртка существующего `modbus_tcp_slave.cpp` в mbedTLS-сессию (mbedTLS уже в проекте, `mbedtls_x509_fatfs.c` уже грузит сертификаты с SD)
- Хранение ключей: приватный ключ устройства — Flash sector 6–7 (уже зарезервирован), CA и клиентские сертификаты — SD (`/sec/`), загрузка через веб-страницу «Безопасность»

#### Режим B: WireGuard-туннель — для сложных сетей

- Устройство само поднимает исходящий UDP-туннель к серверу заказчика → решает NAT без APN; Modbus TCP, веб и всё остальное — внутри туннеля
- WireGuard: минимальный код (ChaCha20-Poly1305, X25519, BLAKE2s), roaming-friendly, устойчив к смене сетей — идеален для мобильных устройств
- mbedTLS 3.x уже содержит ChaCha20-Poly1305 и X25519; BLAKE2s — ~300 строк кода
- Оценка: +25–35 KB Flash, ~10 KB RAM. Реализуемо на F407
- Режим B также даёт защищённый доступ к веб-интерфейсу через GSM — бонус

#### Матрица выбора

| Сценарий | Рекомендуемый стек |
|---|---|
| Корпоративный заказчик со своей SCADA | APN + MBAPS (802) |
| Заказчик без APN, устройства в поле | WireGuard + Modbus TCP внутри |
| Максимальная паранойя (КИИ) | APN + WireGuard + MBAPS поверх |
| LAN-объект (Ethernet/WiFi) | MBAPS (802), 502 закрыт или read-only |

### Уровень 3. Безопасность устройства по IEC 62443-4-2

Целевой уровень: **SL1 на старте → SL2 к серийной версии**. Категории требований:

| Категория 62443-4-2 | Реализация в MonSet |
|---|---|
| IAC — идентификация и аутентификация | Роли viewer/operator/engineer/admin; уникальный Device ID; mTLS для машинных клиентов |
| UC — управление использованием | Матрица прав: viewer — только чтение; operator — тест отправки; engineer — LAD/конфиг; admin — безопасность и ключи |
| SI — целостность системы | Подпись прошивки + проверка в bootloader (этап 2); CRC и откат LAD-программы; read-only системные файлы |
| DC — конфиденциальность | TLS 1.2/1.3 везде; шифрование `runtime_config.json` (пароли/ключи) — AES-256-GCM, ключ в Flash |
| RDF — ограничение потоков | Встроенный файрвол: whitelist IP для 502/802; закрытие неиспользуемых портов; отключение веба по расписанию |
| TRE — реагирование на события | Аудит-лог всех действий; алармы безопасности на сервер (неудачные логины, открытие 502 без TLS) |
| RA — доступность ресурсов | IWDG (есть); rate limiting на TCP-соединения; лимит 4 клиента Modbus; таймауты сессий; приоритет скан-цикла над веб |

**Аппаратный задел на SL3:** в следующей ревизии платы — secure element ATECC608A на I2C1 (шина уже есть): аппаратное хранение ключей, secure boot, анти-тампер.

## 3. Российский регуляторный контур

| Документ | Применимость к MonSet |
|---|---|
| ГОСТ Р МЭК 62443 (нац. адаптация IEC 62443) | Методологическая основа; ссылка в ТУ и паспорте устройства усиливает позицию в тендерах |
| 187-ФЗ + Приказ ФСТЭК № 239 | Обязателен для **значимых объектов КИИ** заказчика. MonSet позиционируем как техническое средство мониторинга (не СЗИ); для объектов 1–2 категории — только вне контура значимых систем или через сертифицированные шлюзы заказчика |
| ПП РФ № 1119 | Для КИИ 3-й категории — базовые меры: наши TLS/RBAC/аудит покрывают типовые требования |
| ГОСТ-криптография | Не требуется для общепромышленного применения. Для КИИ с требованием ГОСТ — внешний сертифицированный криптошлюз (КриптоПро и аналоги) на стороне заказчика; нативная ГОСТ-реализация — отдельная дорожная ветка, не стартуем |

Честная граница: сертификация MonSet как СЗИ (ФСТЭК) — отдельный дорогой проект (1+ года). Стратегия: продавать как АСУ ТП / мониторинговый комплекс, соответствующий IEC 62443-4-2 SL1–SL2 по архитектуре, без формальной сертификации СЗИ на первом этапе.

## 4. План реализации (коммиты в migration)

| Этап | Содержание | Затронутые файлы |
|---|---|---|
| S1 | RBAC: роли в веб-авторизации, матрица прав на API | `web_server.cpp`, `runtime_config.cpp` |
| S2 | Страница «Безопасность»: загрузка сертификатов, политика паролей | `www/security.html`, `web_server.cpp` |
| S3 | MBAPS: TLS-обёртка Modbus slave, порт 802, mTLS, whitelist Unit ID | `modbus_tcp_slave.cpp`, `mbedtls_x509_fatfs.c` |
| S4 | Шифрование секретов в конфиге (AES-256-GCM, ключ в Flash sector 6) | `runtime_config.cpp` |
| S5 | Файрвол: whitelist IP, rate limiting, лимиты сессий | `w5500_net.cpp`, `modbus_tcp_slave.cpp` |
| S6 | Аудит безопасности: события входа, отказы, смена ключей | `circular_log.cpp` + audit (из спеки) |
| S7 | WireGuard-туннель (опция) | новый `wg_tunnel.cpp` |
| S8 | Подпись прошивки + secure bootloader | отдельный проект bootloader |

Зависимости: S3 требует готового mTLS-хранилища (S2/S4). S7 независим, но после S5.

## 5. Принятые решения по открытым вопросам спецификации

| Вопрос | Решение |
|---|---|
| Размер сегмента бэкапа | 256 KB, квота 2 MB на параметр — **принято** |
| Лимиты LAD | 128 ранг / 1024 элемента / 2 ПИД — **принято** |
| Пин ADC батареи | Назначаем свободный (не PA4/PB1/PC5 — они под AI); финализировать при правке `board_pins.hpp` |
| Хранение файлов | Все файлы на microSD платы (как сейчас) |
| Modbus TCP через GSM | APN + MBAPS (порт 802) + опционально WireGuard — этот документ |
